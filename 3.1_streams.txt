Лабораторная работа 3.1: Подсчёт событий в окне с использованием Kafka Streams
Цель: Создать простое Java-приложение Kafka Streams, которое подсчитывает количество сообщений в топике за последние 30 секунд и выводит результат в реальном времени.

Почему Java и Kafka Streams? Kafka Streams — это JVM-библиотека (Java/Scala): официальных «нативных» библиотек потоковой обработки для Python/Go нет. В лабах 2.2/2.3 мы отправляли и читали сообщения из Python-клиентов (confluent-kafka) — простую оконную логику можно написать и там, но окна, join-ы, восстановление состояния после рестарта и масштабирование Kafka Streams даёт «из коробки». Альтернатива без написания кода — ksqlDB (см. лабу 4). Эта лабораторная — первое знакомство с Java и Maven в курсе: код уже написан, ваша задача — собрать проект и запустить.

Ориентиры:
- Первая сборка Maven скачивает зависимости и плагины из Maven Central — заложите 5-15 минут и доступ в интернет до https://repo.maven.apache.org (проверка сети — в шаге 3).
- Нужна Java 21: проверьте JAVA_HOME (echo $JAVA_HOME; как задать, если пусто — в шаге 3).

Где и под каким пользователем выполняем:
- Подключаемся по ssh kafka1.lab.
- Шаги 2-4 (создание проекта, сборка, запуск приложения) выполняем под пользователем kafka: переход — sudo -u kafka bash (или su - kafka); рабочий каталог — /home/kafka/kafka-streams-lab.
- Если открыли новый терминал — повторите переход: ssh kafka1.lab, затем sudo -u kafka bash.
- Консольные продюсер и консьюмер (шаг 5) можно запускать в любом терминале kafka1.lab.

Создайте файл src/main/java/com/lab/WindowCounter.java:
package com.lab;

import org.apache.kafka.clients.consumer.ConsumerConfig;
import org.apache.kafka.common.serialization.Serdes;
import org.apache.kafka.streams.KafkaStreams;
import org.apache.kafka.streams.KeyValue;
import org.apache.kafka.streams.StreamsBuilder;
import org.apache.kafka.streams.StreamsConfig;
import org.apache.kafka.streams.Topology;
import org.apache.kafka.streams.kstream.Grouped;
import org.apache.kafka.streams.kstream.KGroupedStream;
import org.apache.kafka.streams.kstream.KStream;
import org.apache.kafka.streams.kstream.KTable;
import org.apache.kafka.streams.kstream.Produced;
import org.apache.kafka.streams.kstream.Suppressed;
import org.apache.kafka.streams.kstream.TimeWindowedKStream;
import org.apache.kafka.streams.kstream.TimeWindows;
import org.apache.kafka.streams.kstream.Windowed;

import java.time.Duration;
import java.util.Properties;
import java.util.concurrent.CountDownLatch;

public class WindowCounter {
    public static void main(String[] args) {
        // Конфигурация Kafka Streams
        Properties props = new Properties();
        props.put(StreamsConfig.APPLICATION_ID_CONFIG, "window-counter-v1");
        props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka1.lab:9092,kafka2.lab:9092,kafka3.lab:9092");
        props.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.String().getClass());
        props.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.String().getClass());
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
        // Гарантия обработки: включаем exactly-once (идемпотентный продюсер + транзакции).
        // Kafka 3.0+; в курсе Kafka 4.1.1 константа EXACTLY_ONCE_V2 есть — если в вашей версии
        // её нет, используйте строку "exactly_once_v2".
        props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, StreamsConfig.EXACTLY_ONCE_V2);
        // Внутренние топики приложения (changelog/repartition) Kafka Streams создаёт сам.
        // Без явного значения они получат broker-дефолт replication.factor (обычно 1) —
        // зададим 3, как у входных топиков.
        props.put(StreamsConfig.REPLICATION_FACTOR_CONFIG, 3);
        // По желанию: резервная копия локального состояния на другом хосте кластера
        props.put(StreamsConfig.NUM_STANDBY_REPLICAS_CONFIG, 1);

        StreamsBuilder builder = new StreamsBuilder();

        // 1. Читаем поток из входного топика
        KStream<String, String> inputStream = builder.stream("streams-input");

        // 2. Присваиваем ключ "total" всем сообщениям (чтобы считать их вместе)
        KStream<String, String> keyedStream = inputStream
            .selectKey((key, value) -> "total");

        // 3. Группируем по ключу
        KGroupedStream<String, String> grouped = keyedStream
            .groupByKey(Grouped.with(Serdes.String(), Serdes.String()));

        // 4. Применяем перекрывающееся (hopping) окно: 30 секунд, шаг 10 секунд (окна
        //    перекрываются на 20 секунд; sliding-окна в Kafka Streams — отдельный механизм).
        //    Grace 5 секунд: опоздавшие сообщения ещё успевают попасть в окно до его закрытия.
        TimeWindowedKStream<String, String> windowed = grouped
            .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofSeconds(30), Duration.ofSeconds(5))
                .advanceBy(Duration.ofSeconds(10)));

        // 5. Считаем количество сообщений в каждом окне. Без suppress() count() эмитит новое
        //    значение на КАЖДОЕ сообщение (в streams-output шёл бы поток 1, 2, 3, ... на окно),
        //    поэтому промежуточные апдейты подавляем: наружу идёт только итог по закрытому окну.
        KTable<Windowed<String>, Long> counts = windowed
            .count()
            .suppress(Suppressed.untilWindowCloses(Suppressed.BufferConfig.unbounded()));

        // 6. Преобразуем итог по закрытому окну в читаемый формат и отправляем в выходной топик
        counts.toStream()
            .map((windowedKey, count) -> {
                // Форматируем вывод: [окно] -> количество
                String windowInfo = String.format("[%s - %s]",
                    windowedKey.window().startTime().toString(),
                    windowedKey.window().endTime().toString());
                return new KeyValue<>(windowInfo, count.toString());
            })
            .to("streams-output", Produced.with(Serdes.String(), Serdes.String()));

        // 7. Также выводим результат в консоль для наглядности
        counts.toStream()
            .foreach((windowedKey, count) -> {
                System.out.printf("Окно: %s - %s | Сообщений: %d%n",
                    windowedKey.window().startTime(),
                    windowedKey.window().endTime(),
                    count);
            });

        Topology topology = builder.build();
        System.out.println("Топология приложения:");
        System.out.println(topology.describe());

        KafkaStreams streams = new KafkaStreams(topology, props);
        CountDownLatch latch = new CountDownLatch(1);

        // Обработка завершения
        Runtime.getRuntime().addShutdownHook(new Thread("streams-shutdown") {
            @Override
            public void run() {
                System.out.println("Завершение работы...");
                streams.close();
                latch.countDown();
            }
        });

        try {
            System.out.println("Запуск Kafka Streams приложения...");
            streams.start();
            latch.await();
        } catch (Exception e) {
            System.err.println("Ошибка: " + e.getMessage());
            System.exit(1);
        }
    }
}

Вопросы для самопроверки:
Что происходит с сообщениями, если приложение Kafka Streams перезапустить?
Подсказка: AUTO_OFFSET_RESET_CONFIG задан "earliest" (см. код) — но он влияет только на
ПЕРВЫЙ запуск, когда сохранённых оффсетов ещё нет. При перезапуске поведение определяют:
(а) восстановление локального состояния из changelog-топика — накопленные счётчики окон не
обнуляются; (б) гарантии обработки: включён exactly_once_v2 (см. код) — повторных чтений и
задвоений нет; (в) grace 5 секунд — сообщения, пришедшие позже закрытия окна (старт окна +
30 с + 5 с), в это окно уже не попадут.
Краткий ответ: после рестарта приложение продолжает с сохранённого состояния и оффсетов:
благодаря транзакциям EOS уже прочитанное не перечитывается, а опоздавшие в закрытые окна
сообщения отбрасываются (grace истёк).
Почему мы используем ключ "total" для всех сообщений?
Подсказка: что произойдет, если у сообщений будут разные ключи?
Как изменить размер окна на 1 минуту?

Пояснение к лабораторной работе 3.1: Kafka Streams - Подсчёт событий в окне
Что мы сделали?
Мы создали полноценный пайплайн потоковой обработки данных с использованием Apache Kafka и Kafka Streams:

1. Развернули инфраструктуру
Подготовили три виртуальные машины с Kafka в режиме KRaft (без ZooKeeper)

Настроили репликацию данных для отказоустойчивости (3 реплики)

Создали кластер Kafka, способный обрабатывать миллионы сообщений в секунду

2. Реализовали приложение потоковой обработки
Создали Java-приложение на Kafka Streams API
Реализовали логику подсчёта событий в перекрывающемся (hopping) окне:
Размер окна: 30 секунд
Шаг окна (advance): 10 секунд — соседние окна перекрываются на 20 секунд
Агрегация: подсчёт количества сообщений
Итог выводится по закрытии окна (30 с + grace 5 с на опоздавшие сообщения)
Примечание: sliding-окна (SlidingWindows) в Kafka Streams — отдельный механизм (join событий
по времени); в этой лабе используется именно hopping-окно (TimeWindows + advanceBy)
Настроили ввод/вывод данных через топики Kafka
3. Построили полный конвейер обработки
Продюсер → (streams-input) → Kafka Streams → (streams-output) → Консюмер
                     ↓
              Подсчёт в окне
                     ↓
            Вывод в консоль + Kafka
Что мы получили в итоге?
Работающую систему реального времени
Источник данных: продюсер отправляет сообщения каждые 5 секунд
Обработчик: Kafka Streams приложение подсчитывает сообщения в окнах
Результаты: выводятся в консоль И сохраняются в Kafka для дальнейшего использования
Конкретные технические результаты
Топик streams-input - входной поток сырых событий
Топик streams-output - результат обработки (статистика по окнам)
Приложение Kafka Streams:
Автоматически масштабируется (можно запустить несколько инстансов)
Сохраняет состояние (не теряет данные при перезапуске)
Включает exactly-once в границах приложения (в коде: PROCESSING_GUARANTEE_CONFIG =
exactly_once_v2): каждое сообщение входного топика учитывается ровно один раз, без задвоений
при рестартах и ребалансах. Область действия — одно приложение Kafka Streams и его топики;
downstream-консьюмеры должны читать с isolation.level=read_committed
Пример работы системы (сообщение каждые 5 секунд; числа приблизительные — зависят от момента
старта приложения и равномерности отправки)
Сообщения отправляются:     12:00:00, 12:00:05, 12:00:10, 12:00:15, 12:00:20, 12:00:25, ...
Окно [12:00:00 - 12:00:30]: ~6 сообщений (12:00:00 ... 12:00:25)
Окно [12:00:10 - 12:00:40]: ~6 сообщений (12:00:10 ... 12:00:35) — часть сообщений та же,
что и в предыдущем окне
Окно [12:00:20 - 12:00:50]: ~6 сообщений (12:00:20 ... 12:00:45)
Окна перекрываются на 20 секунд (шаг 10 с при длине 30 с), поэтому одно и то же сообщение
(например, 12:00:20) учитывается сразу в нескольких соседних окнах

Ключевые преимущества нашего решения
1. Масштабируемость
Можно запустить 10, 100, 1000 инстансов приложения
Kafka автоматически распределит партиции между инстансами
Пропускная способность растёт линейно

2. Отказоустойчивость
Данные реплицируются на 3 сервера
При падении инстанса Kafka Streams, его партиции перераспределяются
Состояние (count) первично хранится ЛОКАЛЬНО на инстансе (RocksDB, state.dir — по умолчанию
/tmp/kafka-streams/window-counter-v1); changelog-топик приложения (window-counter-v1-*-changelog,
создаётся с RF=3 — параметр REPLICATION_FACTOR_CONFIG в коде) — его реплика для восстановления
после сбоя или рестарта, а не единственное хранилище.

3. Простота эксплуатации
Не нужно отдельный кластер для обработки (используем тот же Kafka)
Автоматическое восстановление после сбоев
Встроенный мониторинг через JMX метрики

4. Точная семантика обработки
Exactly-once в границах приложения Kafka Streams (PROCESSING_GUARANTEE_CONFIG=exactly_once_v2,
включён в коде): чтение входного топика и запись результатов транзакционны, повторных обработок
при рестартах и ребалансах нет
Область действия — одно приложение и его топики: чтобы downstream не увидел незакоммиченных
результатов, он должен читать с isolation.level=read_committed. Сквозной (end-to-end)
exactly-once через несколько независимых систем Kafka Streams не гарантирует — там нужны
транзакции или идемпотентность на стороне приёмника
Сохраняется порядок сообщений в пределах ключа
Гарантированная доставка результатов в выходные топики

Сравнение с прямыми HTTP-вызовами
// СЛОЖНО И НЕНАДЁЖНО:
serviceA → HTTP → serviceB → HTTP → serviceC
// При падении serviceB вся цепочка ломается

// ПРОСТО И НАДЁЖНО (наш подход):
serviceA → Kafka → serviceB → Kafka → serviceC
// При падении serviceB сообщения накапливаются в Kafka и обрабатываются позже
